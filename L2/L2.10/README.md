# sort - реализация GNU sort на Go

Утилита сортировки строк с поддержкой флагов `-n`, `-r`, `-u`, `-M`, `-b`, `-c`, `-h`, `-k`.

## Запуск

```bash
go build -o mysort .
./mysort -n data.txt
cat data.txt | ./mysort -r
```

## Исследование производительности

Тестировалось на файле из 1000000 строк случайных чисел, флаг `-n`.

### Профилирование (pprof)

Для поиска узких мест использовал cpu и mem профили:

```bash
go test -bench=BenchmarkSort -cpuprofile=cpu.prof -memprofile=mem.prof -run='^$'
go tool pprof -top -cum cpu.prof
go tool pprof -top mem.prof
```

### Что я нашёл и исправил в результате профилировки

**1. `sort.SliceStable` и рефлексия**

Первая профилирофка показал что примерно 42% CPU уходит на `reflectlite.Swapper`,т.e. это `sort.SliceStable` использует рефлексию для каждого swap. Заменил на `sort.Stable` с явной реализацией `sort.Interface` для однопоточного пути и на `slices.SortStableFunc` для параллельного.

**2. `fmt.Fprintln` в writeLines**

Примерно 18% CPU тратилось на `fmt.Fprintln` он разбирает аргументы через рефлексию. Для записи строки с переносом это overkill. Заменил на `w.WriteString(line)` + `w.WriteByte('\n')`.

**3. Повторный парсинг в merge**

После добавления параллельной сортировки pprof выявил что около 28% CPU тратит `merge` на `cmpFunc` и `ParseFloat`. Числовые ключи уже были вычислены перед сортировкой, но merge их не использовал и парсил строки заново. Поэтому я ввёл структуру `entry{line, key}`,где ключи сохраняются, merge сравнивает `float64` напрямую.

**4. Параллельная сортировка**

Разбиваю данные на N частей по числу ядер, сортирую в горутинах, сливаю попарным параллельным merge. Как я узнал  GNU sort работает с `--parallel`, по умолчанию!.

### Сравнение с GNU sort

```
=== GNU sort -n (многопоточный) ===
real  0m0.49s
user  0m1.25s

=== mysort -n ===
real  0m1.13s
user  0m1.25s
```

`user` время одинаковое алгоритмически мы на уровне GNU sort. Разница в `real` из-за того что GNU sort эффективнее распараллеливает, так как C чуть быстрее Go.

### Бенчмарки: однопоточный vs многопоточный

```
BenchmarkSortSingle-8      1.0s    137MB    1M allocs
BenchmarkSortParallel-8    0.46s   209MB    1M allocs
```

Параллельность даёт примерно 2x ускорение.

### Итог оптимизации

Начальная версия работала 1.5с на 1М строк. Финальная 0.46с. Ускорение в 3 раза.
